## 一句话本质

> **SSA = 给每一次「赋值」发一个新名字，让「这个值从哪来」永远只有一个答案。**

它解决的是：命令式字节码里同一个局部变量槽会被反复覆盖（`istore_2` 一次次改写槽 2），
导致「某条 `iload_2` 到底读的是哪次写入」需要**反推**。SSA 把「一个会被覆盖的槽」拆成
「一串只写一次的值」，于是数据流分析从「迭代求不动点」退化为「沿定值-使用链走一遍」。

## 俯瞰框架（先看全貌，再钻卡点）

```text
SSA 知识体系
├── A. 为什么需要 SSA
│   ├── 命令式的痛点：变量可被反复覆盖
│   └── SSA 的收益：定值唯一 → 数据流变简单
├── B. 支配关系（SSA 的地基）
│   ├── 支配 / 严格支配 / 直接支配者 idom
│   └── 支配树（本项目：Cooper-Harvey-Kennedy 迭代算法）
├── C. 支配边界（phi 该插在哪）
│   └── DF(b) = { d | b 支配 d 的某前驱，但不严格支配 d }   ⚠️核心卡点
├── D. phi 节点（汇合点按来路取值）
│   └── 为每条前驱边准备一个操作数
├── E. 变量版本化 + 前缀重命名
│   └── 沿支配树 DFS，每槽一个「版本栈」，压入/弹回          ⚠️核心卡点
└── F. 产出：definitions / uses 映射（定值-使用链）
```

对照本项目文件：

```text
com.aetherdecompiler.core.ssa
├── SsaVariable        → 一个「槽 + 版本」的定值标识
├── PhiNode            → 汇合点的 phi 函数
├── DominanceFrontier  → 支配边界（C 层）
├── SsaForm            → 产出容器（F 层）
└── SsaBuilder         → 三阶段算法编排（B→E 全流程）
```

## 关键卡点（⚠️ 需要「微观串行」单独解决的点）

| # | 卡点 | 为什么难 / 易误判 |
|---|------|------------------|
| ⚠️1 | **支配边界为什么正好是 phi 的位置** | 直觉上「汇合点就插 phi」，但只有「定义了变量却支配不到该点」的汇合点才需要，多插会引入多余 phi |
| ⚠️2 | **版本栈的压入/弹回时机** | 进入块压入、离开块弹回；DFS 的「进入/离开」边界极易写错，导致读到错误的版本 |
| ⚠️3 | **phi 操作数按来路边对齐** | 有多个前驱时，操作数顺序必须与「前驱列表」严格一致，否则取值张冠李戴 |
| ⚠️4 | **异常边也算前驱** | `exceptionSuccessors` 会引入额外到达路径，忽略它会导致 phi 操作数填不满 |

> 这四点在本项目的 `SsaBuilder`、`DominanceFrontier` 里都有对应实现与注释，学习时逐个对照。
