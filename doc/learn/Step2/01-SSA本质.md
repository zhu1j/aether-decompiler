# Step2 · 01 为什么需要 SSA（本质）

> TEACH 第 1 步：一句话本质 ＋ 第 2 步：俯瞰框架。

## 一句话本质

> **SSA = 给每一次赋值发一个新名字，让「这个值从哪来」永远只有一个答案。**

## 从一个具体的痛开始

看这段 Java 与它的字节码（本项目 `SsaBuilderTest` 用到的 `Sample.sumTo` 简化版）：

```java
int sum = 0;              // 槽 1 ← 0
for (int i = 1; i <= n; i++) {
    sum += i;             // 槽 1 ← 槽 1 + 槽 2
}
return sum;               // 读槽 1
```

对应的栈式字节码里有大量 `istore_1` / `iload_1`：

```text
iconst_0
istore_1          ; 槽1 ← 0        （第 1 次写槽1）
...
iload_1
iload_2
iadd
istore_1          ; 槽1 ← 槽1+槽2   （第 2 次写槽1）
...
iload_1           ; 读槽1 —— 到底读的是哪一次写的？
ireturn
```

**痛点**：后面那条 `iload_1` 读到的到底是「第 1 次写」还是「第 2 次写」的值？
在命令式视角下，答案是「看哪条路径到达这里」——这需要**数据流分析**去反推。

## SSA 的解法

给每次写入发一个**版本号**，于是槽 1 被拆成 `v1_0`（入口/初值）、`v1_1`（`sum=0`）、
`v1_2`（循环内 `sum+=i`）……每条 `iload` 改写为读取**唯一的**版本：

```text
v1_0 = <入口>
v1_1 = 0
...
v1_2 = v1_1 + v2_x        ; 循环内
...
return v1_?               ; 但循环可能走 0 次或多圈 → 究竟哪一版？
```

循环里 sum 有两条来源（「一次都没进循环」的是 `v1_1`，「至少进过一次」的是 `v1_2`），
所以在循环汇合处需要一种「按来路取值」的节点——**phi**：

```text
v1_3 = phi(v1_1 [从循环外来], v1_2 [沿回边来])
```

这就是后面 [02 支配边界与 phi](02-支配边界与phi.md) 要解决的核心。

## 俯瞰：SSA 得到什么

```text
命令式视图             SSA 视图
槽1 ──写──写──写         v1_0, v1_1, v1_2 ……（每个只写一次）
   ↑ 覆盖                每个使用点 → 唯一的一个版本
```

一旦「每个值只定义一次」，这些分析都变得平凡：

| 分析 | 命令式下 | SSA 下 |
|------|---------|--------|
| 常量传播 | 迭代数据流 | 沿 def-use 链替换 |
| 活跃性 | 反向迭代 | 看有无使用 |
| 死代码消除 | 反复不动点 | 无使用者的定值即可删 |

## 现实场景（你为什么会在乎）

- **反编译器**：要从字节码还原出「像人写的」变量——SSA 是必经的中间层（本项目 Phase2）。
- **静态分析/漏洞检测**：污点传播本质就是在 def-use 链上跑。
- **编译器优化**：寄存器分配、GVN、常量折叠全部建立在 SSA 上。
