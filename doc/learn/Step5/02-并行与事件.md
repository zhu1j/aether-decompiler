# Step5 · 02 并行与事件

> TEACH 第 3 步：微观串行——只解决「并行该由谁负责」这一个卡点。

## 卡点 ⚠️3：线程池该由谁创建

**直觉**：内核自己开一个线程池，用起来最省事。
**问题**：内核一旦「**拥有**」线程池，就会与宿主（比如 JavaFX GUI 的应用线程模型）
冲突——线程数量、命名、生命周期全都不受控，还可能撑爆线程、阻塞界面。

**正解**：内核**不拥有**线程池，只接受**注入**。谁调用、谁决定并行策略：

```java
public List<ClassAnalysis> analyzeAll(ClassSource source, ExecutorService executor)
        throws Exception {
    if (executor == null || names.size() <= 1) {     // 未注入 → 串行
        ...
    }
    List<Future<ClassAnalysis>> futures = new ArrayList<>();
    for (String name : names) {
        futures.add(executor.submit(() -> analyzeClass(source, name)));   // 类级并行
    }
    for (Future<ClassAnalysis> f : futures) {
        out.add(f.get());                            // ⚠️ 按输入顺序收集
    }
    return out;
}
```

要点：

1. **类与类独立**，天然可并行；类内方法共享缓存，顺序处理即可；
2. **结果顺序与输入一致**：用 `Future` 列表按提交顺序 `get()`，避免结果乱序；
3. **异常不被吞**：`f.get()` 会把子任务异常重新抛出（卡点 ⚠️4）。

## 便捷入口（可选的「自带池」）

为方便命令行场景，另给一个便捷方法：自己建池、用完即关：

```java
public List<ClassAnalysis> analyzeAll(ClassSource source) throws Exception {
    int n = Math.max(1, Runtime.getRuntime().availableProcessors());
    ExecutorService pool = Executors.newFixedThreadPool(n);
    try {
        return analyzeAll(source, pool);
    } finally {
        pool.shutdown();                             // 保证回收
    }
}
```

> 注意：这是**调用方**（此处为本类的便捷包装）在拥有线程池，而非内核引擎的常驻状态——
> 生命周期被严格限定在一次调用内，用 `try/finally` 保证 `shutdown`。

## 卡点 ⚠️4：失败要能传递

并行最容易被忽略的是「异常逃逸」：子任务抛的异常若被吞掉，调用方会拿到一个「看似成功
但缺内容」的结果。本项目通过 `Future.get()` 让异常**重新抛出**，与串行路径行为一致。

## 事件：让进度可见

流水线每个阶段完成时发布一个事件（仅当绑定了总线）：

```java
public DecompilationPipeline withEventBus(com.aetherdecompiler.api.EventBus bus) { ... }

private void publish(AetherEvent.Phase phase, IRKind kind, String message) {
    if (bus != null) bus.publish(new AetherEvent(phase, kind, message, null));
}
```

阶段依次为 `CFG → SSA → AST`。GUI 据此点亮 Stage 指示器、更新进度——**引擎只管
「发生了什么」，界面决定「怎么显示」**，两者通过事件解耦。

## 一句话记住

```text
内核不拥有线程池，只接受注入。类级并行、结果保序、异常穿透。
事件发布阶段完成，界面负责呈现。
```
